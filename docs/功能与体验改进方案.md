# XiXiの徒步小记 · 加功能 / 改体验 具体方案

> 基准：2026-10-19（v1.2.4.5 / vc291）· 功能已冻结，新增须点名
> 定位铁律：**日记本（记录 + 回顾），不是专业徒步工具**；「零服务端」是核心资产，任何方案**不得引入服务端**
> 用户原话（本方案的尺子）：**「日记本重要的是打开，不是提醒」**

---

## 一、判断依据（先说清"为什么提这些"）

现有功能已经相当完整：那年今日 · 里程碑庆祝卡 · 年度回顾 · 热力图 · 山册（按山聚合）· 分享卡 · 计划 + 原生闹钟提醒 · WebDAV 备份 · 导出/导入。

所以**不该再加"更多功能"，该加"更多打开的理由"**。按这个尺子排：

| 方向 | 问的问题 | 价值 |
|---|---|---|
| **A 回顾** | 打开就能看到过去的自己吗？ | 高（贴定位） |
| **B 记录** | 记一条要费多少劲？ | 中 |
| **C 输出** | 回忆能带走/分享吗？ | 中 |
| **D 数据** | 会不会丢？ | 中高 |
| E 工具型（路线/GPS/海拔图） | —— | **不做**（背离日记本定位） |

---

## 二、方案清单（按建议优先级）

### ★ P0-1 「时光机」—— 把「那年今日」的命中率从"一年 1 天"提到"大部分日子"

**问题**：现有「那年今日」只匹配**同月同日**（`app-data.js` → `renderOnThisDay()`）—— 一年只有一次，绝大多数日子**整卡不渲染**（宁缺毋滥）。结果就是"打开大多时候看不到回忆"，与定位最矛盾的一处。

**做法**：三层回退，命中就用：
1. 同月同日（现有，保留）
2. **同月**：去年/前年**这个月**你去了哪座山（"去年的十月，你在…"）
3. **N 天前**：如 100 天前 / 365 天前的那条（"100 天前的今天"）

**改动面**：只改 `app-data.js` 一个函数（约 30 行）+ 卡片文案微调；样式沿用现有卡。
**铁律检查**：纯本地计算、零新依赖、不碰 JS 引入顺序 ✅
**风险**：极低（沿用现有卡片与失败兜底 `try/catch`）
**预期**：打开概览页时"有回忆可看"的概率大幅上升

---

### ★ P0-2 备份健康提示 —— 只提示一次，不唠叨

**问题**：日记本最怕**丢数据**。现在有"上次同步时间"，但**得自己去看**；很久没备份不会有任何提醒。
**做法**：超过 N 天（建议 30）没成功备份 → 概览页底部出现一条**可关闭**的温和提示（"数据已 32 天没备份，去设置看看？"），点一次"知道了"就**永久不再提**（本地记标记）。
**改动面**：`app-data.js`（读 `上次备份时间` + 渲染一条提示）+ 一个「已忽略」标记。
**铁律检查**：不引入服务端（只读本地已有状态）✅
**风险**：低。**★注意别做成"唠叨"** —— 所以是"一次即止"，且**绝不弹窗**（只做页内一条）。

---

### P1-1 「随机一天」—— 给"打开"一个轻量惊喜

**做法**：概览页放一个小入口（图标按钮，不占版面）；点一下**随机**取一条旧记录 → 直接开现有「记录详情」弹窗。
**改动面**：小（随机取一条 + 复用 `openRecordDetailModal`）。
**铁律检查**：纯本地 ✅
**风险**：极低。

---

### P1-2 「这座山，上次来是…」—— 让重复去同一座山有累积感

**问题**：山册（按山聚合）已经能看"这座山去过几次"，但**没有时间纵深**。
**做法**：山册卡片 / 记录详情里显示"上次来是 X 天前"，并可与上次**对比海拔/里程**（差值）。
**改动面**：中（山册数据结构已有，加时间序对比）。
**铁律检查**：纯本地 ✅
**风险**：低。

---

### P1-3 「一句话快记」—— 降低录入摩擦

**问题**：日记本的命脉是"记下来"。如果每次都要走完整表单（日期/难度/海拔/照片…），会劝退"就想记一笔"的场景。
**做法**：记录页「＋」里多一个**极简模式**：只填**名字 + 日期**就能存，其余留空、之后随时补（列表里显示"未补全"小标）。
**改动面**：中（表单校验放宽 + 列表标记）。
**铁律检查**：纯本地 ✅
**风险**：中（要小心别打破现有表单校验与统计口径 —— 空值统计要兜底）。

**★需先确认**：现有「添加徒步记录」选择卡是否已支持"直接新建"到某种简略程度 —— 若有，则本项降级为"只加未补全标记"。

---

### P2-1 年度画册导出（带照片）

**问题**：现在导出有"纯文字回忆册"，但**没有照片**。
**做法**：把一年的记录 + 照片渲染成"多页长图"或一组图片，可保存 / 分享（复用分享卡的 canvas 思路）。
**改动面**：大（照片读取 + canvas 排版 + 分页）。
**铁律检查**：纯本地 ✅（但 canvas 用本地照片，注意 IndexedDB 读取量）
**风险**：中（工作量最大的一项）

## 三、明确**不做**的（避免走偏）

| 想法 | 为什么不做 |
|---|---|
| GPS 轨迹 / 海拔曲线 / 配速分析 | 那是"专业徒步工具"，不是日记本 |
| 云同步（自有服务器）/ 账号体系 | **直接违反「零服务端」铁律** |
| 社交 / 好友 / 排行榜 | 同上（要服务端），且破坏"私密日记"属性 |
| Web Push / 服务端定时提醒 | 需存推送端点 → 推翻隐私承诺（用户已明确不做） |
| 天气 API 自动填充 | 引入外部依赖（离线自足铁律说"禁任何外部 CDN/外链"） |

---

## 四、建议的推进顺序

1. **P0-1 时光机** —— 改动最小、最贴"打开就能看回忆"，先做
2. **P0-2 备份提示** —— 数据安全，一次即止
3. **P1-1 随机一天** —— 顺手做（和 P0-1 同属"回顾"）
4. P1-2 / P1-3 —— 等前三个发出去、看你的使用感受再定
5. P2-1 年度画册 —— 单独排一轮（工作量大）

**发版建议**：上述任一项都是**用户可感知的新功能**，按规矩应**升号**（不是同号重发）。
