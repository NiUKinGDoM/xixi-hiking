## 1. 现状（都是实测事实，非推测）

- **零账号代码**：全项目无 `login / oauth / token` 相关实现。
- 唯一的「云」是 **WebDAV**：配置字段 `{ server, username, password }`，存 key `hiking_sync_config`；密码经 `encPwd()` 混淆后落盘。
- **同步配置入口（③ 已落地）**：设置页是**账号卡**（显示网盘类型/账号、密码脱敏），点「绑定账号」弹 `#syncBindModal`（**② 服务商预设：坚果云 / 其他 WebDAV**）；旧的内联三输入框（`#syncServer` 等）已移除。
- 备份包内容：`xixi-data.json`（记录+计划+照片引用）+ `photos/*.jpg` + `回忆册.html` —— **④ 已落地：可选含同步配置**（默认带「服务器+账号」，可勾选「连应用密码一起带上」并明确警告）。
- **无二维码 / 扫码能力**；项目铁律禁止任何外部 CDN（离线自足）。
- **换机现状（v1.2.1.8 后）**：从云端下载备份恢复 → **账号密码一键配好**，不用再手填三样。（应用密码长度各服务商规则不同，文档不再写死「16 位」）

## 2. 为什么不建议走「真账号」

| 路径 | 覆盖 APK？ | 代价 |
|---|---|---|
| **平台托管云服务**（Auth + Database） | ❌ **大概率不行** | 登录按**访问域名精确校验**；APK 是本地包（域为 `localhost`），网页版 `pages.dev` 也不是它分配的域 → 要用就得把 App 改成「加载线上页面」，直接砸掉「没信号也能用」 |
| **自建后端** | ✅ | 买服务器 + 长期运维 + 域名/证书 + **用户数据的第一责任人变成你** |
| **微信 / QQ 登录** | ✅ | 需开放平台资质（个人主体审核门槛不低）+ 接入与回调维护 |

**共性代价（只要做真账号就跑不掉）**：注册/找回密码、隐私政策、账号注销入口、数据导出、跨用户数据隔离、被投诉要处理 —— 对一个个人徒步日记 App，这些负担与「换机少输两个框」的收益严重倒挂。

## 3. 推荐方案（零后端，APK / 网页版通用）


### ① 同步配置码 —— 核心

- **旧机**：设置页新增「导出同步配置」→ 生成一串码（可复制；后续可加显示二维码）。
- **新机**：设置页新增「导入同步配置」→ 粘贴 → 自动填好表单 → 一键「测试连接」→ 拉取数据。
- **编码内容**：`{ v:1, server, username, password? }` → JSON → 压缩 → base64（一行为主，便于复制/扫码）。
- **★安全设计（重要）**：
  - **默认不含密码**，新机手输一次 —— 因为现有 `encPwd()` 是**固定 key 的异或混淆**（`app-core.js:321`），强度只够"防明文躺本地"，**绝不能用来保护一串会给别人看的码**。
  - 含密码必须**用户主动勾选** + 明确警告「这串码包含你的应用密码，别发给任何人」。
  - 不做"有效期/一键失效"（纯前端无此能力），改为提示用户**导出后及时删掉聊天记录**。
- **二维码 / 扫码**：需引入**本地二维码库**（禁 CDN）+ 扫码需 Capacitor 原生插件 → 建议**第一期只做粘贴**（零依赖），二维码作为第二期增强。

### ② 预设服务商 —— 把 3 个输入框变 2 个

- 表单加「服务商」快捷选择：点「坚果云」→ `#syncServer` 自动填 `https://dav.jianguoyun.com/dav/`。
- 附「应用密码怎么拿」的图文引导（设置 → 安全选项 → 应用密码）+ 一键跳转。
- 顺带把标签文案从「服务器地址（WebDAV）」这类术语，改成用户能懂的说法。

### ③ 入口文案「登录化」 —— 只改观感，不改机制

- 把「配置服务器 / 账号」呈现为「绑定账号 / 登录」的观感（填一次 = 登录态）。
- **诚实文案**：要让人明白这是**绑定你自己的网盘账号**，不是「注册了 XiXi 的账号」——避免误解与后续投诉。
- 纯 UI 改动（文案/图标/分组），不动同步逻辑。

## 4. 将来若真要做账号（路线图，暂不启动）

- **触发条件**：真要做分享卡互动 / 好友 / 排行榜这类**跨用户**功能。
- **那时再评估**：轻量自建服务，或"平台云服务 + App 改为线上壳"（并接受离线能力下降）。
- **必须同步准备**：隐私政策、账号注销、数据导出、跨用户隔离 —— 这些是配套成本，不是可选项。
- **结论**：现在不必为它背上后端。

## 6. 风险与注意事项

- **安全**：现有 `encPwd` 强度不足，配置码**不得**依赖它保护密码（见 §3①）。
- **设计规范**：改动设置页会触碰 `tools/designcheck.js` 的圆角/字体/玻璃规范与 E2E 像素断言 → 必须跑全套自检。
- **iOS 网页版**：相机/扫码能力在浏览器里受限，若做扫码需加能力守卫（`tools/ioscheck.js`）。
- **发版节奏**：按项目惯例 —— 改完 www 先部署预览 → 用户真机验收 → 说「同步」才发版。
